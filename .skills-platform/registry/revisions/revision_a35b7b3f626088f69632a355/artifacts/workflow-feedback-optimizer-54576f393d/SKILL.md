# Workflow Feedback Optimizer

## 목적

프로젝트의 구축 절차 안에서, 현재 단계가 요구하는 워크플로우 산출물을 만들고 개선한다. 재사용할 단계 지시문·실행 전략·허용된 구조를 수정하며, 근거에 맞는 검증 수준으로 다음 담당 단계에 인계한다.

참조 문서가 읽히지 않으면 필요한 계약이 없는 상태로 처리한다. 명시적 프로젝트 정책은 그 범위에서 적용하며, 이 스킬을 수정 권한의 근거로 사용하지 않는다.

## 0. 구축 절차 인식 — 필수 진입 관문

모든 호출은 이 관문에서 시작한다. 기존 인식 기록이 있으면 최신성부터 검사하여 전체 인식, 변경분 인식, 유효한 기록 재사용 중 하나를 수행한다.

### 0.1 정본과 호출 목적 확인

사용자 요청, 프로젝트의 구축 절차 정본, 작업 상태, 대상 파이프라인 정본을 실제로 읽는다. 기존 자료로 해결되는 항목을 사용자에게 다시 묻지 않는다. 읽지 못한 자료는 읽은 것으로 표시하지 않는다.

**구축 절차**는 파이프라인을 어떻게 정의·구현·검증·반영하는가이고, **실행 파이프라인**은 만들어진 시스템이 입력을 어떻게 처리하는가이다. 두 단계 ID를 구분한다.

### 0.2 구축 과정과 현재 위치 파악

프로젝트 고유의 단계·분기·병렬 진행·재작업 경로를 보존한다. 각 관련 단계의 목적, 입력, 수행 활동, 책임자, 산출물, 완료 조건과 실패 시 복귀 위치를 확인한다.

이번 호출의 기준 단계, 진행 상태, 선행 산출물, 남은 결정, 현재 편집 범위를 식별한다. 전체 과정을 새로 설계하거나 완료된 앞 단계를 다시 수행하는 것으로 자동 전환하지 않는다.

### 0.3 산출물과 실행 단계 연결

각 변경 대상에 대해 정본 위치·revision·담당 구축 단계·사용하는 실행 단계를 연결한다. 생성된 복사본이면 원본과 재생성 경로를 찾는다. 단계별 지시문을 고치는 일과, 그 지시문을 작성하는 구축 방법을 고치는 일을 구분한다.

### 0.4 호출·검증·반환 계약 확인

왜 지금 호출되었는지, 무엇을 제출해야 하는지, 어떤 기준으로 검사할지, 누가 받는지, 성공·실패 시 어느 단계로 돌아갈지 확인한다. 실제 도구·권한·예산은 이번 작업에 필요한 범위로 연결한다.

### 0.5 인식 결과 명시

[구축 맥락 템플릿](assets/construction-context-template.md)의 읽어 되짚기 형식으로 목표·현재 단계·수정 대상·고정 조건·검증 범위·인계 위치를 기록한다. 출처 없는 보완은 `proposed` 또는 `unresolved`로 구분한다.

[구축 절차 인식](references/construction-intake.md)의 관문 조건으로 `ready`, `partial`, `blocked`, `stale`을 판정하고, 지금 가능한 작업과 불가능한 작업을 따로 적는다. `ready`는 실행·반영·배포 승인이 아니다.

구축 절차가 없으면 필요한 최소 절차를 `proposed` 초안으로 작성한다. 이 초안 작성만 예외적으로 허용하고, 아직 없는 절차를 이미 승인된 정본으로 간주하지 않는다.

## 1. 현재 단계의 작업 범위 확정

인식 결과에 따라 이번 호출을 설계, 검토, 실패 분석, 후보 작성, 비교 검증, 반영 또는 인계 중 필요한 작업으로 한정한다. 이 분류는 호스트의 구축 단계 이름을 바꾸지 않는다.

작업 기준선에는 관련 정본의 식별값을 연결한다. 초기 구축에서는 불완전한 설계도 기준선으로 삼을 수 있으나, 구현·실행 완료로 표시하지 않는다. 수정 허용 범위, 완료 기준, 비교 방법과 예산을 확인한다.

## 2. 산출물 작성 또는 관측 확보

설계 단계이면 현재 단계의 입력으로 필요한 산출물을 작성하고 문서·계약 일치 여부를 검토한다. 이미 정해진 목표와 다른 단계의 책임을 임의로 재정의하지 않는다.

실행 가능한 단계이면 허용된 환경에서 기준선을 실행하고 실제 입력·출력·도구 결과를 기록한다. 기존 증거를 재사용하면 기준선·사례·환경·실행 경로의 일치를 확인한다. 도구가 없으면 설계 검토와 실행 계획까지만 수행한다.

## 3. 평가와 피드백 연결

고정된 기준과 관측을 비교한다. 설계 불일치, 실제 실행 실패, 가상 예제를 구분한다. 설계 의존 관계 또는 실제 실행 경로를 따라 실패와 관계 있는 수정 위치를 찾는다.

피드백에는 관측, 위반 기준, 원인 가설, 정본 위치, 담당 구축 단계, 변경안, 재검증·재작업 범위를 연결한다. 원인 가설은 확정 사실로 쓰지 않는다.

현재 단계의 수정 범위를 벗어나면 [통합 계약](references/integration.md)의 재작업 인계로 반환한다. 상위 단계가 소유한 계약 문제를 하위 프롬프트 문구로 우회하지 않는다.

## 4. 후보 작성과 검증

허용된 최소 변경을 후보로 작성한다. 설계 후보는 설계 기준으로, 실행 후보는 사전에 고정된 실행 평가로 검증한다. 실행 단계의 변경은 영향받는 후속 단계를 재실행하고, 성능 채택 전에는 전체 파이프라인을 비교한다.

설계 검토 통과와 실행 품질 개선을 구분한다. 구조·평가·권한이 바뀌면 해당 인식 기록과 비교 기준선을 다시 확인한다. 미실행 검사를 통과로 처리하지 않는다.

## 5. 반영과 구축 절차 복귀

[운영 계약](references/contract.md)의 조건과 실제 적용 권한을 충족할 때만 현재 정본에 반영한다. 설계 문서 반영은 그 문서 범위의 채택이며, 런타임 검증이나 배포 승인이 아니다.

반영 직전 관련 정본의 revision이 달라졌으면 `stale`로 처리하고 재인식한다. 여러 파일의 부분 반영을 전체 반영으로 표시하지 않는다.

[작업 요청·인계 템플릿](assets/work-order-template.md)으로 산출물, 검증 범위, 미해결 사항, 영향받는 단계, 반환할 단계와 다음 행동을 보고한다. 호스트 단계 상태의 실제 변경은 권한 있는 호출자에게 맡기며, 직접 변경했다면 도구 결과를 남긴다.

종료 시 현재 정본·인식 기록·최소 증거·재개 위치만 유지한다. 사용자 온보딩 설명과 에이전트 재개 정보를 분리한다.
