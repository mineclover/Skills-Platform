# 구축 절차 인식 계약

## 1. 기능과 범위

이 절차는 스킬이 프로젝트의 구축 과정을 작업 가능한 맥락으로 읽어들이는 필수 진입 관문이다. 결과는 **무엇을 읽었고, 지금 어디에서 무엇을 할 수 있으며, 결과를 어디로 돌려보낼지**를 확인하는 `WorkflowContext`다. 이는 참조 중심의 작업 기록 이름이며, 전용 데이터베이스나 JSON 스키마를 요구하지 않는다.

기존 워크플로우 문서를 요약하는 데 그치지 않고 구축 과정의 목적·활동·의존 관계·산출물·완료 기준·현재 위치를 파악한다. 전체 방법론을 이 스킬의 고정 단계로 교체하지 않는다.

## 2. 구분할 대상

| 대상 | 질문 | 예시 |
|---|---|---|
| 구축 절차 | 어떤 과정으로 파이프라인을 만드는가? | 요구 정리 → 계약 설계 → 구현 → 검증 |
| 실행 파이프라인 | 완성된 시스템은 입력을 어떻게 처리하는가? | 탐색 → 근거 수집 → 판정 → 정리 |
| 구축 산출물 | 각 구축 단계가 만들고 관리하는 것은 무엇인가? | 요구 문서, 데이터 계약, 지시문, 테스트 |
| 스킬 호출 | 현재 구축 작업 중 스킬이 맡는 일은 무엇인가? | 계약 누락 검토, 판정 지시문 개선 |

하나의 산출물은 여러 실행 단계에서 사용될 수 있다. 하나의 구축 단계가 여러 산출물을 만들 수도 있다. 이름이 같다는 이유로 구축 단계와 실행 단계를 일대일 대응시키지 않는다.

기본 개선 대상은 실행 파이프라인을 정의하는 산출물이다. 구축 방법·호출 정책 자체의 변경은 별도 수정 범위가 명시된 작업에서만 제안한다. 스킬의 안전·채택 정책은 개선 대상으로 삼지 않는다.

## 3. 공식 인식 절차

### I0. 출처와 대상 확정

| 항목 | 수행 내용 |
|---|---|
| 입력 | 이번 요청, 기존 인식 기록, 구축 절차·작업 상태·파이프라인의 정본 위치 |
| 수행 | 실제 자료를 읽고 어떤 자료가 어떤 정보의 정본인지 확인한다. revision을 기록하고 충돌을 구분한다. |
| 산출 | 정본 참조표, 이번 작업 대상, 신규 인식·변경분 인식·재사용 여부 |
| 완료 조건 | 목표와 대상이 특정되고, 필요한 자료의 접근 가능 여부가 드러난다. |

사용자가 특정 자료를 이번 정본으로 지정한 경우 그 범위를 적용한다. 안전·권한을 문서의 문구만으로 확장하지 않는다. 문서끼리 충돌하고 유효한 우선순위도 없으면 어느 것을 임의로 선택하지 않는다. 영향 없는 검토는 계속하고 해당 결정·수정만 막는다.

### I1. 목표와 구축 의도 파악

최종 사용자의 입력·출력, 성공 조건, 보존해야 할 제약과 이번 구축 과제가 해결하려는 문제를 읽는다. 단계가 분리된 이유나 선후 관계에 영향을 주는 결정이 있으면 그 정본을 참조한다.

산출은 목표·제약 참조와 이번 호출이 기여해야 할 결과다. 모든 과거 토론을 복원할 필요는 없다. 확정된 결정의 의미와 이번 작업에 필요한 이유만 남긴다.

### I2. 구축 과정 추출

아래 항목을 프로젝트의 원래 단계 이름과 ID에 연결한다. 현재 단계와 선행 조건, 영향받는 후속 단계는 상세하게 읽고 나머지는 참조로 유지한다.

| 항목 | 인식할 내용 | 필수 범위 |
|---|---|---|
| 단계 식별 | ID, 이름, 담당자·역할, 해당 절차·하위 절차 | 현재·관련 단계 |
| 목적 | 이 단계에서 해결할 문제, 최종 목표와의 관계 | 현재·관련 단계 |
| 진입 조건 | 필요한 선행 산출물과 승인·준비 조건 | 현재 단계 |
| 수행 활동 | 읽기·결정·작성·실행·검토 중 실제로 해야 하는 일 | 현재 단계 |
| 산출물 | 결과 형식, 정본 위치, 받는 단계 | 현재·영향 단계 |
| 완료 조건 | 검사 항목, 필요한 증거, 완료 판정 주체 | 현재 단계 |
| 실패 처리 | 재시도·보완·상위 단계 재작업·중단 경로 | 현재·영향 단계 |
| 진행 관계 | 선행, 분기 조건, 병렬 경로, 합류 조건 | 호출에 필요한 범위 |
| 변경 경계 | 지금 편집 가능한 대상과 잠겨 있는 계약 | 이번 변경 영향 범위 |

작업 활동을 인식하지 않은 채 단계 이름만 추출한 것은 완료로 보지 않는다. 순서뿐 아니라 분기·병렬·재작업을 보존한다. 관련 없는 전체 조직 프로세스까지 요구하지 않는다.

### I3. 산출물·책임·실행 단계 연결

| 항목 | 의미 |
|---|---|
| `artifact_ref` | 실제 정본 경로·문서 ID·앵커와 revision |
| `owner_stage` / `owner_role` | 이 내용을 결정·수정하는 구축 단계와 담당 주체 |
| `consumers` | 입력으로 받는 구축 단계 및 사용하는 실행 단계 |
| `edit_scope` | 이번 호출에서 수정할 수 있는 위치와 종류 |
| `preserve` | 의미·형식·동기화에서 보존할 계약 |
| `source_or_generated` | 정본인지 생성물인지, 생성물이면 원본·재생성 방법 |
| `verification_ref` | 해당 산출물에 적용할 검사와 완료 기준 |

예: `계약 설계 단계 → contracts/evidence.md → collect·verify 실행 단계`.

공유 산출물은 모든 관련 소비자를 영향 분석에 포함한다. 담당 단계가 불명확하면 후보 제안은 가능하지만 정본 반영과 단계 이동은 막는다. 근거가 없으면 소유자를 자동 지정하지 않는다.

### I4. 현재 진척과 기준선 확인

이번 호출의 기준 단계, 활성 상태인 다른 단계, 완료·진행·차단·재작업 상태, 아직 결정되지 않은 항목, 잠금 조건을 확인한다. 프로젝트의 상태 어휘를 유지한다.

기준선은 관련 구축 절차, 대상 산출물, 평가 계약, 변경 권한 정책의 revision을 가리킨다. 실행이 필요한 경우에만 실행 환경·사례 버전을 추가한다. 불완전한 초안도 명시적으로 초안 기준선으로 기록할 수 있다.

완료 단계가 있어도 그 산출물의 revision이 바뀌면 필요한 재검토 범위를 식별한다. 과거 완료 표시만으로 현재 유효하다고 간주하지 않는다. 외부 변경을 감지할 수 없으면 인식 시점과 반영 전 재확인 조건을 남긴다.

### I5. 호출 위치와 인계 연결

호출 이유, 기대 산출물, 평가 범위, 출력 수신자, 성공·실패·차단 시 복귀 단계와 다음 행동을 지정한다. 상세 계약은 `references/integration.md`가 소유한다.

스킬을 호출한다는 선언과 실제 호스트에 연결된 상태를 구분한다. 자동 호출을 원한다면 호스트의 실제 trigger·command·오케스트레이터 연결 근거가 필요하다. 연결할 도구가 없으면 통합 제안으로 남긴다.

### I6. 인식 결과 읽어 되짚기

다음 내용을 참조와 함께 반환 또는 기록한다.

```text
목표: 어떤 파이프라인을 왜 만드는가.
현재: 어떤 구축 단계에서 무엇을 진행 중인가.
입력: 어떤 선행 산출물과 revision을 사용했는가.
작업: 이번 호출이 어떤 산출물을 만들거나 고치는가.
경계: 어떤 위치를 바꿀 수 있고 무엇을 보존하는가.
검증: 어떤 증거로 어디까지 완료를 말할 수 있는가.
인계: 누가 받아 어느 단계에서 무엇을 이어 하는가.
미확정: 아직 모르는 항목과 그 때문에 막히는 행동.
```

이 기록은 모델 내부가 학습했다는 증명이 아니라 명시적인 작업 해석이다. 기존 지시·정본으로 충분하면 매번 사용자 확인을 요구하지 않는다. 사용자가 확인하지 않은 것을 `user_confirmed`로 표시하지 않는다. 선택·승인이 필요한 미확정 사항만 해당 권한자에게 넘긴다.

### I7. 관문 판정

아래 질문에 이번 호출 범위에서 답할 수 있어야 `ready`다.

| 검사 | 통과 조건 |
|---|---|
| 대상 구분 | 구축 절차와 실행 파이프라인, 이번 작업 대상이 구분된다. |
| 위치 | 현재 기준 단계와 실제 수행 활동·진입 조건이 특정된다. |
| 출처 | 사용할 정본·산출물·revision에 접근했거나 부재가 명시된다. |
| 책임 | 변경 대상의 소유 단계·소비자·허용 범위가 확인된다. |
| 결과 | 기대 산출물과 그 완료·검증 조건이 정해져 있다. |
| 인계 | 받는 주체, 반환 단계, 다음 행동이 연결된다. |
| 위험 | 필수 미확정·권한·부작용·비교 조건을 별도로 판정했다. |

‘문서 부재’ 자체가 이번에 만들 대상이면 부재를 확인한 것으로 진입할 수 있다. 다만 없는 승인·기준·도구를 존재한다고 채워서는 안 된다.

| `alignment_status` | 뜻 | 다음 행동 |
|---|---|---|
| `ready` | 이번 작업을 해석하는 데 필요한 맥락이 확인됨 | 개별 행동의 권한·도구·검증 조건을 확인한 범위에서 진행 |
| `partial` | 국소 작업은 특정되지만 전체 범위에 미확정이 있음 | 영향을 받지 않는 설계·검토·후보 제안만 진행하고 제한 명시 |
| `blocked` | 이번 목표·위치·핵심 경계 등 필수 맥락이 없음 | 부족한 정보·결정과 준비 산출물을 반환; 변경·실행·반영 중단 |
| `stale` | 기존 기록이 관련 정본·권한·현재 상태와 달라짐 | 영향 범위를 다시 읽고 판정; 오래된 범위로 반영 금지 |

`ready`여도 실제 도구가 없으면 실행할 수 없다. 모든 실행 권한이 있어도 설계만 요청된 호출에서는 실행하지 않는다. 맥락 상태, 도구 가능 여부, 작업 요청 범위는 독립적으로 확인한다.

## 4. 구축 절차가 없는 경우

사용자 요구에서 이번 목표에 필요한 최소 단계·산출물·완료 조건·복귀 경로를 **절차 제안**으로 작성한다. 고정된 전체 개발 생명주기를 강요하지 않는다. 이 제안 작업을 하기 위해 또 다른 구축 절차를 요구하지 않는다.

제안과 확인된 요구를 구분하고, 적용할 근거가 확보되면 I0~I7로 들어간다. 승인되지 않은 절차의 채택·배포는 하지 않는다. 초안 작성은 사용자의 설계 요청 범위에서 가능하며, 현재 프로젝트 상태를 바꾸는 것과 구분한다.

## 5. 재인식과 무효화

| 변화 | 다시 확인할 범위 |
|---|---|
| 구축 단계·진행 관계·담당 주체 변경 | 단계 지도, 소유권, 현재 위치, 호출·인계 |
| 호출 위치·작업 목적 변경 | 현재 단계, 기대 산출물, 허용 행동, 반환 경로 |
| 지시문·계약 등 대상 정본 변경 | 해당 산출물 기준선, 소비자, 후보·증거의 적용 가능성 |
| 평가 기준·사례·모델·도구 환경 변경 | 비교 기준선과 실행 검증; 과거 점수의 직접 비교 금지 |
| 권한·예산·외부 부작용 정책 변경 | 행동 허용 범위와 실제 반영·재실행 조건 |
| 긴 작업 재개·새 에이전트 인계 | 저장된 참조와 현재 revision을 비교한 후 변경분 인식 |

현재 맥락 하나를 갱신하고 불필요한 전체본을 누적하지 않는다. 변경이 없는 재호출은 유효성 확인 후 기록을 재사용한다. 변경된 독립 영역이 현재 작업에 영향이 없다는 근거가 있으면 전체 재인식을 생략할 수 있다.

## 6. 사용자 온보딩과의 분리

절차 인식은 에이전트의 필수 작업이다. 프로젝트 설명이나 사용법을 사용자에게 길게 다시 안내하는 것은 별도의 선택적 온보딩이다. 이미 인식된 맥락에서는 현재 단계와 재개 행동으로 바로 진입하고, 사용자가 요청하지 않은 전체 설명을 반복하지 않는다.
