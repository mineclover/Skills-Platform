# 워크플로우 통합 계약

## 1. 역할

이 문서는 스킬의 **호출 위치·작업 요청·반환·재작업 연결**을 정의한다. 프로젝트가 사용하는 문서·이슈·오케스트레이터에 의미를 대응시키면 되며, 특정 런타임이나 API 형식을 강제하지 않는다.

| 구성 | 책임 |
|---|---|
| 구축 절차의 담당자·호스트 | 현재 단계, 단계 이동, 작업 배정, 완료·재작업 판정 |
| 이 스킬 | 구축 절차 인식, 한정된 산출물 작성·검토·개선, 근거와 인계 작성 |
| 프로젝트 정본 | 목표·단계·계약·지시문·평가·권한의 실제 정의 |
| 실제 도구·실행기 | 파일·문서 변경, 테스트·파이프라인 실행, 관측, 호스트 상태 갱신 |

같은 에이전트가 여러 역할을 맡아도 된다. 역할 간 권한과 검증 범위는 유지한다.

## 2. 통합 위치 정의

스킬을 넣는 각각의 위치에 아래 내용을 연결한다. 이것을 `binding`이라고 부르지만 전용 설정 파일을 요구하지 않는다.

| 정보 | 내용 |
|---|---|
| 위치 | 어느 구축 절차·단계·분기에서 호출하는가 |
| 호출 조건 | 진입 직전, 산출물 생성 후, 검증 실패 후 등 무엇이 호출 계기인가 |
| 작업 목적 | 작성·검토·분석·후보 제안·비교 검증·반영 중 무엇을 맡기는가 |
| 입력 | 인식 기록 또는 정본 참조, 현재 산출물, 필요한 실행 증거 |
| 기대 결과 | 다음 단계가 사용할 산출물과 완료 조건 |
| 작업 경계 | 수정 위치, 읽기·작성·실행·반영 가능 범위, 실제 권한 근거 |
| 반환 | 결과 수신자, 성공·재작업·차단 시 대상 단계와 다음 행동 |
| 반복 제어 | 동일 작업 재호출 처리, 반복·비용 상한, 새 근거 없는 반복 중지 |

다음은 배치할 수 있는 **제안 위치**이며 프로젝트 단계 이름이 아니다.

| 위치 예시 | 맡길 작업 | 다음 단계에 제공할 것 |
|---|---|---|
| 구축 작업 시작 전 | 절차·현재 위치 인식 | 유효한 맥락과 이번 작업 범위 |
| 계약 초안 작성 후 | 단계 책임·입출력·완료·실패 경로 검토 | 누락·충돌·수정 위치·담당 단계 |
| 지시문 작성 후 | 고정 계약 반영·수정 경계 검토 | 검토된 지시문 후보·미확정 |
| 실행 검증 실패 후 | trace 기반 실패 분석·후보·비교 | 변경안·검증 결과·재작업 범위 |
| 정본 반영 전 | 기준선 최신성·채택 조건 확인 | 반영 결과 또는 보류 근거 |

호출 조건을 문서에 적는 것만으로 자동 실행이 설치되지는 않는다. 실제 호스트 연결 상태는 `proposed` 또는 `connected`로 표시하며 `connected`에는 실제 등록 근거를 연결한다.

## 3. 호출 입력 — WorkOrder

아래는 의미 계약이다. 기존 이슈나 문서의 참조를 사용할 수 있다. 매번 같은 내용을 복사하지 않는다.

| 필드 | 설명 | 필요 시점 |
|---|---|---|
| `work_id` | 이번 작업 식별값; 재시도 시 같은 목적·기준선이면 재사용 가능 | 모든 호출 |
| `construction_context_ref` 또는 정본 참조 | 읽을 구축 절차·작업 상태·산출물 | 모든 호출 |
| `at_stage` | 이번 호출의 기준 구축 단계; 병렬 단계는 별도 참조 | 모든 호출; 없으면 인식 절차에서 해소 |
| `requested_action` | 이번 요청이 허용한 작업과 기대 결과 | 모든 호출 |
| `target_refs` | 실제 변경·검토 대상 및 revision | 대상 특정 후 |
| `constraints_ref` / `authority_ref` | 보존 조건·권한·예산 | 관련 행동 전 |
| `criteria_ref` | 산출물 검사·채택 조건 | 완료·채택 판단 전 |
| `evidence_refs` | 설계 검토 자료 또는 실제 실행·비교 증거 | 평가 종류에 따라 |
| `return_to` | 받는 주체, 단계, 다음 행동, 완료 조건 | 통합 작업 수행 전 |

읽을 수 있는 정본에서 해소되는 값은 다시 질문하지 않는다. 시작부터 모든 필드를 사용자 입력으로 강요하지 않고, 인식 절차에서 채운다. 필수 값의 해소 실패는 맥락 상태와 행동 제한에 반영한다.

## 4. 반환 — WorkResult

| 필드 | 반드시 구분할 의미 |
|---|---|
| `work_id` / `context_ref` | 어떤 호출·인식 결과에 대한 반환인가 |
| `alignment_status` | 구축 과정·현재 위치 인식 상태 |
| `result_status` | `designed`, `candidate`, `accept`, `reject`, `blocked` 중 해당 결과 |
| `scope` / `artifact_refs` | 어느 산출물을 어떤 범위로 작성·검토·반영했는가 |
| `verification` | 증거 종류, 실행 여부, 검사 결과와 주장 가능한 범위 |
| `decision_refs` | 변경·채택·보류 판단의 최소 근거 |
| `open_items` | 미해결 항목, 담당, 막히는 행동 |
| `invalidated_refs` | 재검토·재실행할 이전 산출물·증거·단계 |
| `handoff` | 다음 담당자, 대상 단계, 해야 할 일, 진입·완료 조건 |
| `host_state_update` | 실제로 호스트 상태를 바꿨는지와 그 증거; 없으면 `not_performed` |

`verification`에는 `design_review`, `runtime_test`, `comparative_eval`, `none` 등 실제 종류와 `passed`, `failed`, `partial`, `not_run`을 구분한다. 실제 증거가 mock·replay이면 환경 표시를 추가한다. 가상 예제는 항상 `illustrative`다.

인계 유형은 `continue`(현재 범위 완료 후 진행), `rework`(소유 단계로 수정 이관), `hold`(필수 결정·증거 대기), `finish`(호출 종료) 중 하나로 표시할 수 있다. 이 값은 호스트 전이 명령이 아니라 제안·인계 결과다.

## 5. 실패를 구축 단계로 돌려보내는 규칙

실행 경로를 추적하는 축과, 발견된 변경을 소유 구축 단계로 돌려보내는 축을 구분한다.

```text
실패 결과 → 실제 실행 단계 → 문제와 연결된 정본
                              → 해당 정본을 소유한 구축 단계
                              → 재작업 산출물·검증·복귀 위치
```

| 발견 내용 | 반환 대상의 결정 방식 | 피해야 할 처리 |
|---|---|---|
| 필요한 입력은 전달됐지만 지시가 잘못 적용됨 | 해당 지시문을 소유한 단계; 현재 허용 범위면 국소 변경 | 관계없는 모든 단계 지시문 수정 |
| 입력 필드 자체가 정의되지 않음 | 입출력 계약의 소유 단계 | 마지막 프롬프트에서 없는 값을 추정 |
| 계약에는 필드가 있지만 전달 코드가 누락됨 | 실제 변환·전달 구현의 소유 단계 | 맞는 계약까지 변경 |
| 분기·완료·실패 경로가 정의되지 않음 | 실행 구조의 소유 단계 | 지시문에 숨은 분기를 추가해 계약 우회 |
| 평가가 목표·계약과 충돌함 | 평가 기준의 소유 단계로 독립 이슈 전달 | 후보가 통과하도록 평가 완화 |
| 승인·도구·데이터가 부족함 | 해당 자원·권한의 담당자 | 프롬프트 개선 성공으로 대체 |

역할 이름은 예시다. 실제 프로젝트의 매핑을 사용한다. 정적 문서에서 발견한 문제는 설계 결함으로, 실제 trace에서 발견한 문제는 관측된 실행 실패로 분류한다. 인과관계는 충분한 증거가 없는 한 가설로 유지한다.

상위 계약 변경으로 기존 산출물의 유효성이 깨질 수 있으면 `invalidated_refs`에 영향받는 지시문·구현·테스트를 지정한다. 관련 없는 단계까지 전부 재작업시키지 않는다. 재작업 후 원래 검증 위치로 돌아올 조건을 함께 정한다.

## 6. 재개·동시 수정·반복 호출

재개 기록에는 현재 정본과 revision, 이번 작업 상태, 남은 결정, 다음 행동과 필요한 입력을 둔다. 재개 시 인식 기록의 최신성을 확인한 뒤 그 위치에서 이어간다. 전체 사용자 온보딩을 반복하지 않는다.

반영 직전에는 관련 정본의 최신 revision을 확인한다. 변경이 있으면 자동 덮어쓰기·자동 병합을 하지 않고 영향 재인식과 필요한 검증을 수행한다. 수정하지 않는 참조 문서라도 권한·평가에 영향을 주면 최신성을 확인한다.

호스트가 같은 `work_id`를 재전달하면 기존 반환과 적용 여부를 먼저 확인한다. 이미 반영된 패치를 재적용하지 않는다. 외부 부작용은 호스트가 보장하는 멱등성·승인 정책 없이는 재실행하지 않는다.

스킬 결과가 자동으로 자신을 무제한 재호출하도록 연결하지 않는다. 실패 ID·기준선·새 증거·예산으로 새 반복의 필요성을 판정하고, 새 신호가 없으면 종료한다. 이 패키지는 이러한 호스트 제어 코드를 구현하지 않는다.
