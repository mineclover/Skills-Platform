# 예제: 구축 절차가 없을 때와 중간 작업 재개

아래 내용은 모두 `illustrative`인 행동 예시다. 실제 프로젝트 구축·승인·도구 실행 결과가 아니다.

## 1. 구축 절차 정본이 없는 새 작업

### 요청

```text
문서를 입력받아 분류하고 검토할 항목을 추려주는 파이프라인을 설계해줘.
아직 구축 절차나 지시문은 없다. 먼저 설계까지 진행해.
```

### 인식과 허용 작업

정본이 없다는 사실과 ‘설계까지’라는 요청 경계를 기록한다. 존재하지 않는 절차를 읽었다고 하지 않는다. 준비되지 않은 외부 실행·자동 반영은 하지 않는다.

이번 목표에 필요한 최소 구축 과정의 제안을 작성한다. 예를 들어 분류 기준을 정하고, 단계별 입출력·검토 반환을 정의하고, 실행·평가 준비 과제를 인계하는 순서다. 이것은 가상 프로젝트용 제안이며, 모든 프로젝트에 같은 단계를 요구하지 않는다.

### 결과 시연

```text
출처 상태: proposed.
인식 상태: partial — 기존 구축 절차·담당·실행 조건은 아직 없다.
가능한 행동: 사용자의 요청 범위에서 절차와 대상 파이프라인 초안을 작성한다.
불가능한 행동: 승인된 실행 절차로 간주, 외부 데이터 실행, 배포·운영 상태 변경.
결과: designed — 절차 제안, 단계·입출력 초안, 미정 항목·다음 담당 작업.
인계: 분류 기준과 외부 입력 취급 정책을 결정할 작업으로 연결한다.
```

초안 작성에 또 다른 상위 구축 절차의 정의를 요구하지 않는다. 스킬의 최소 초안 작성 규칙으로 재귀를 끊는다. 제안이 명시적 요청이나 유효한 정책에 따라 채택되면 그 정본을 읽고 공식 인식 관문으로 들어간다.

## 2. 기존 맥락으로 중간부터 재개

### 저장된 상태 가정

```text
구축 단계: C-contract에서 계약 작성 완료, C-prompt에서 지시문 작성 중.
정본: build.md@demo-b1, contract.md@demo-c1, prompt.md@demo-p1.
다음 작업: prompt.md의 실패 분기를 작성하고 계약과 대조한다.
```

### 재개 시 확인

정본 revision과 현재 작업 상태를 확인한다. 모두 같으면 기록 재사용 후 실패 분기 작성에서 바로 이어간다. 사용자에게 처음부터 전체 온보딩을 반복하지 않는다.

`contract.md`만 `demo-c2`로 바뀌었다면 변경분을 읽고 프롬프트·완료 조건·검증 영향 범위를 다시 인식한다. 관련 없는 다른 워크플로우가 바뀐 것만으로 전체 프로젝트를 다시 분석하지 않는다.

### 변경 영향이 있으면

`demo-c2`가 새로운 실패 반환 필드를 요구하면 기존 프롬프트 후보와 검토 근거는 영향 범위에서 `stale`이다. 최신 계약을 반영하고 필요한 검토를 반복하기 전에는 과거 통과 표시로 반영하지 않는다.

## 3. 호출은 정상인데 실행 도구가 없는 경우

현재 단계·목표·수정 경계·복귀 위치를 모두 확인했다면 맥락은 `ready`다. 그러나 요청된 실행에 필요한 도구가 없으면 결과는 `blocked`가 될 수 있다.

이 경우 실행 계획·필요 capability·검증 사례 준비는 인계하되, 테스트 실행·성능 개선은 주장하지 않는다. 맥락의 완전성과 실행 가능성을 하나의 상태로 합치지 않는다.

## 4. 수정 후보를 다른 사람이 먼저 반영한 경우

같은 작업이 재호출되면 현재 정본과 기존 결과를 확인한다. 후보가 이미 반영되어 있으면 다시 적용하지 않고 실제 상태에 맞는 인계만 반환한다. 다른 수정이 반영되어 기준선이 달라졌으면 `stale`로 처리한다.

이 행동은 스킬 지침이다. 동시성 잠금·멱등 실행·상태 전이는 실제 호스트가 지원하는 기능과 권한으로 구현해야 한다.
